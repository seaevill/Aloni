## New
**M1. MUST, 0022:22–29 (`spray_floor_crops`) + 0023:55–61 + 0022:117–119: a crop whose label has NO PHI/REI counts as "has a label", and the gate then has no floor for it.**
- `missing` counts only crops with no label row at all, and `max(phi_days)` skips NULLs.
- Repro as the owner:
  - Crop B has a signed label (PHI 3, REI 24). Crop C has a draft label of the same product with `phi_days` and `rei_hours` NULL. That is an ordinary owner insert, accepted.
  - The A+B-style job holds C and B, and its spray is unknown, 4 days old.
  - The owner types PHI 3 / REI 24 as a correction. It is **accepted** (`sl.missing = 0`, `sl.phi = 3`).
- Harvest of the crop-C planting is then **accepted on day 4, by the owner and by the worker b2**. `lf.n = 1` and `lf.phi` is NULL, so no floor clause fires, and the stored `phi_until` has passed.
- The same works for REI only: crop C has a PHI but REI NULL.
- This breaks safety rule 1: a missing value must mean blocked.
- Fix:
  - In `spray_floor_crops`, count as `missing` every crop that has no applying label with **both** `phi_days` and `rei_hours` non-null. Alternatively, aggregate per crop and refuse when any crop's PHI or REI is NULL.
  - In the gate, add `or lf.phi is null or lf.rei is null` (unknown = closed).

**M2. MUST, 0025:154–160 (`complete_spray_job` REI lock): the worker's «Έγινε» reads only the stored `s.rei_until` of earlier sprays, not the REI of the planting's own crop.** The m7 N1 fix covered the harvest gate (lf.rei) but not this lock.
- Repro as worker b2. Setup:
  - A legacy row: a crop-B label (REI 24) on an A+B job, ended 30 h ago. Crop A's own signed label says REI 48.
  - A new planned job for b2 on the crop-A planting.
- Result: `complete_spray_job` **succeeds**, with `flags: []` and no `rei_conflict`. The worker enters a field whose re-entry period for that crop runs for 18 more hours.
- Such rows can exist in two ways:
  - (a) They are already in production. 0021 matched the label per job, and m7 notes that mixed lettuce/rocket jobs are normal for Bora.
  - (b) Even after 0022, they can be made again by the race in S1.
- Fix: in the conflict query, also block when `spray_floor_planting(...)` for `other.planting_id` gives `n = 0`, a NULL REI, or `s.sprayed_at + lf.rei >= p_ended_at`. That is the same predicate as the gate, for REI.
- Before apply, run this read-only check on production:
  `select s.id, s.job_id from job_spray s join label_uses l on l.id = s.label_use_id join job_plantings jp on jp.job_id = s.job_id join plantings pl on pl.id = jp.planting_id where s.phi_source = 'label' and pl.crop_id <> l.crop_id;`

**S1. SHOULD, 0022:128–135 vs 0023:26–28: the "no link after spray" check is a race.** Neither trigger locks the job.
- Repro with two owner sessions:
  - T1 opens a transaction and links a crop-A planting to job J3, which holds only crop B. T1 stays open.
  - T2 inserts a spray on J3 with the crop-B label (`phi_source='label'`, PHI 3) and commits.
  - T1 commits.
- Result: J3 now holds crop A with a crop-B label PHI.
- The harvest gate still held: the crop-A floor of 14 days blocks.
- The worker path can race in one order too. The FK's KEY SHARE lock waits for `complete_spray_job`'s `FOR UPDATE`, but the BEFORE trigger has already checked by then.
- The resulting row feeds M2, and it shows a wrong PHI for planting A in the register.
- Fix: take `perform 1 from jobs where id = new.job_id for update` (or `pg_advisory_xact_lock` on the job id) in both `forbid_link_after_spray` and `check_spray_record` before their checks.

**S2. SHOULD, 0011 `harvest_conflicts` (applied, unchanged by 0022+): the "record, then show the conflict" side was not updated to the m6/m7 rules.**
- Owner harvests dated more than 5 min back are not gated. That was decided on 2026-11-18 (0011, DECISIONS l.56/62), and the view is the compensating record.
- But the view uses only `s.phi_until`/`s.rei_until` and the latest `sprayed_at`. It has no per-planting floor and no earliest end.
- Repro as the owner: a harvest of the crop-A planting on the legacy A+B job, dated 10 min back on day 4, while crop A's floor (PHI 14) runs. It is accepted (by design), and `harvest_conflicts` **shows 0 rows** for it.
- Fix: a new migration that redefines the view with the gate's predicate (`spray_floor_planting`, `spray_first_end`). It can ship with 0022+.
- Related, same design: the 5-minute owner window gates only at `now()`. A harvest dated now−4 min, when PHI ended at now−2 min, is accepted. The worker is gated at both times.

**S3. SHOULD, 0031:111: a worker may name ANY live worker of the farm as `cut_by`.**
- Repro as worker b2 (roster entry Giorgos): harvests with `cut_by` = Ahmet, and with `cut_by` = "Cutter" (a roster entry with no user), are both accepted.
- The file's own comment says the worker's phone sends her own roster entry. The server does not enforce it.
- This is attribution in the harvest record, not PHI.
- Fix: for a worker-only session, require `w.user_id = auth.uid()`. If a foreman must record harvests for others, decide that with Bora and write it in DECISIONS.

**S4. SHOULD, 0030 + RUNBOOK §14 step 4: the scheduler's credential is the full service-role key.**
- RUNBOOK §14 step 4 has Bora paste the service-role key as a literal into the SQL Editor, which keeps query history and snippets.
- The key is then stored a second time (Vault) and sent through pg_net, whose request queue holds the headers until the request is sent.
- Nothing leaks today, but this is not least privilege for a job that only has to start a function.
- Fix:
  - Use a dedicated random token (a function secret, for example `WEATHER_CRON_TOKEN`, plus the same value in Vault). The function compares against that token.
  - Create the Vault secrets through the dashboard's Vault UI rather than as SQL literals.
- On first apply, check on the real project that `authenticated`/`anon` have no SELECT on `net.http_request_queue` or `net._http_response`. The stub cannot show this.
