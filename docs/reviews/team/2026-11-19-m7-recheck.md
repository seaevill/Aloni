## New
N1. **MUST, 0022:20/24, 0022:54–55, 0025:75, 0015:53 (finding 5 not finished):** one spray job holds a crop-A planting (no label for A) and a crop-B planting (signed label, PHI 3). All three repros below were run as the owner:
- (a) The spray takes the crop-B label (`phi_source='label'`). **Harvest of the crop-A planting is accepted on day 4.**
- (b) The job holds only crop B when it is sprayed. A crop-A planting is **linked afterwards**: `job_plantings` guards UPDATE only (0015:53), not INSERT. Harvest of A is accepted on day 4.
- (c) The spray is unknown, and the owner types PHI 3/REI 24 as a correction. The floor comes from crop B, the typed value is accepted, and harvest of A is accepted on day 4.

The worker's "Έγινε" goes through `complete_spray_job` and takes the same branch (0025:75 sees crop B in the job, so the state is `signed`). Mixed lettuce/rocket jobs on one parcel are normal for Bora.

Fix:
- The gate and the floor read labels for the **planting's own crop** (`new.planting_id`).
- A spray whose label is of another crop counts as unknown for that planting.
- INSERT into `job_plantings` is refused once the job has a spray.

N2. **MUST, 0022:46 + 0022:96/101 (rest of A1):** the owner records an unknown-PHI spray ending at now+4 min (allowed by the 5-minute tolerance) and harvests the planting at once. The harvest is accepted (repro, one transaction). A phone clock running a few minutes fast is enough, for example when a spray and a harvest sync in the same batch. The worker is not exposed: `complete_spray_job` refuses `p_ended_at > now()` (0025:57). Fix: for `t >= now()`, count every recorded spray (`x.fe <= t or t >= now()`), or compare against `t + interval '5 minutes'`.

N3. **SHOULD, 0023:83–84:** the movements are now matched by content plus `m.created_at >= o.created_at`. Nothing ties them to the correction's transaction any more, and `created_at` is a column the phone may send (it is not in `server_owned`, 0012:38). Repro as the owner through `apply_ops`:
- Transaction 1 stores `in 1` and `out 9` (`created_at` 2099-01-01) on their own.
- A later, separate transaction stores the qty-9 correction alone. It is applied and committed.

One forged movement can satisfy every later correction with the same lot and quantity. This is ledger integrity, not PHI. The error text still says "in the same transaction". Fix: match on `m.sync_xid = pg_current_xact_id()`, which the server sets (0010:38) and which is the top-level transaction even inside a savepoint. Also make `created_at` server-owned for `stock_movements` and `job_spray`.

N4. **LOW, 0029:45–49:** `weather_fetch_state.farm_id` is not tied to the parcel's farm (no composite FK). Only the service role writes it, so the risk is low.
